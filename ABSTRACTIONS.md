# What the models establish

The `.spthy` files are ideal symbolic trace models, not computational proofs of BBS, AMF, HPKE, or their composition. No authentication, secrecy, answer, or consent theorem is installed as a restriction. The sole restriction initializes each trusted service once. All `[reuse]` helpers must themselves verify. `no_precomp`, the goal-ordering oracle, and `hide_lemma` annotations change proof search, not protocol traces.

## Cryptographic operations

| Operation | Representation and adversarial capabilities |
|---|---|
| Enrollment signatures | `sign(message, secret)` is an opaque public constructor, with no destructor exposing the secret. `Token` records an honestly issued signature and its complete signed statement. Verification matches the received token against this relation. There is one honest ES and no ES-key compromise. |
| Pairing BBS proof | A fresh opaque handle and a private `Proof(handle, number, bundle, hidden-pseudonym, challenge)` relation. Honest generation and `Adversary_Prove_Token` create it. The latter requires network knowledge of the signature, pseudonym, and challenge. Each invocation has fresh randomness. The verifier checks the received handle's statement and challenge; possession of a private relation alone never delivers a network message. Existing handles can be replayed. |
| Delegation | An explicit signature checked under the **attested owner's** delegation public key, including number, delegate bundle, expiry label, and originating-call scope. The signature can be constructed by an attacker who learns the owner's secret. There is no general recursive delegation verifier. |
| AMF | A fresh signature handle plus `Amf(handle, message, sender-public-key, receiver-bundle, authority-public-key)`. Both sender signing and **receiver forgery** are available to the adversary upon knowledge of the respective secret. The verifier must receive the actual handle in the authenticated ciphertext and match all relation fields. The receiver is an honest local process holding its own bundle. This abstracts designated verification; it does not model `Judge`, receiver binding for accountability, or deniability equivalence. The judge's key is never exposed and judge forgery is not modeled, consistent with the paper's trust in the LEA. |
| External credential component | Credential generation and validation are assumed operations, outside Julep’s verification scope. The current model represents their output as `pok(signature, hidden-subject, challenge, randomness)` with disclosed policy and attribute alongside it. The verification pattern checks issuer, policy, and challenge; no destructor exposes the witness. These encode assumed interface behavior, not a proof of credential soundness, holder binding, or privacy. Julep’s obligations concern disclosure control and transport of this output. |
| AEAD | `aead(message,key,nonce,AD)` with correct-key/AD decryption and a public nonce projection. Honest senders choose fresh nonces. Anyone knowing the key can encrypt the same plaintext using a different nonce; the key update hashes the signed plaintext transcript and signs a state/index commitment in requests. Key-derivation comparison tests appear in the [findings’ supporting checks](MODELING_FINDINGS.md#supporting-verification-checks). AD includes index, message type, and role. The labeled index/encryption subkeys in the paper are abstracted by domain-separated index hashing and use of the shared state as the encryption key. |
| Pairing PKE | Tamarin's perfect asymmetric encryption, with separate `rsp` and `fin` plaintext tags. This includes ciphertext integrity/non-malleability assumptions beyond IND-CPA confidentiality. Randomized PKE ciphertext identity is abstracted away; pairing's KDF contains plaintext transcripts, not these ciphertext bytes. Key privacy is not proved by these trace models. |
| DH and KDF | Tamarin's DH equational theory and an opaque `kdf`. Pairing requires received shares to match `g^x`, an ideal non-identity group-element check. It does not give a participant the discrete logarithm. The paper now requires the corresponding group, subgroup, and encoding validation. |

A concrete PKE implementation must still establish the stated confidentiality and key-privacy properties; these trace results do not establish that any particular HPKE configuration meets every requirement.

`Token`, `Proof`, and `Amf` are ghost relations implementing ideal verification algorithms. They are not network services or channels in the proposed protocol. These abstractions assume the relevant primitive properties; they do not assume that the protocol authenticates the right peer, agrees on the right transcript, or keeps the derived key secret. Those are separate lemmas. The explicit attacker creation rules are essential: removing them would overstate security.

The request commitment `h(<ratchet-context, current-state, index>)` (the model spelling of the paper's `H(ratchet, K, idx)` domain) is recomputed and checked before accepting the signed request. This ties authentication to the state instance even when encryption keys are exposed; the response nonce binds the entire signed request.

The original secret-key pattern matching was not by itself a secret-key leak. For example, matching `sign(m,sk)` against a known verification key `pk(sk)` can represent signature verification. None of our verification rules outputs the matched secret. The revised relations primarily avoid repeatedly expanding large transcript terms and make the attacker's operations explicit.

## Authentication and transcript simulation

The authentication lemmas concern honest devices running the specified protocol against an outside network attacker. The proof events are internal records of those modeled actions; a third party does not obtain them by inspecting a claimed transcript. Alice deliberately fabricating a transcript is a different scenario: she can use her own private keys, the shared state, public enrollment material, and peer information already available to her. This is the paper’s intended deniability argument for ordinary third parties, with the designated judge as the stated exception.

The AMF abstraction includes receiver forgery when the adversary knows the designated receiver’s private key. Authentication lemmas exclude exposure of either relevant endpoint’s long-term keys, so this capability is not an outside attacker’s route to impersonation in the protected case. Modeling that capability does not itself prove the full deniability requirement: the suite does not compare the views from genuine and simulated pairing/CA transcripts and does not model the judge’s accountability checks. In particular, a simulator is not granted a previously undisclosed peer identity merely because it can fabricate cryptographic messages. The forgeability witnesses `deniability_witness_ca_request`, `deniability_witness_ca_response`, and `deniability_witness_icv_request` exhibit executions in which the receiver, represented by the attacker holding only the receiver's long-term keys, the shared key, and a peer identity the peer had already disclosed, produces a message its own verification accepts without the peer. They establish non-attributability of transcripts, not indistinguishability. These distinctions follow the paper’s stated simulation scope and the [AMF definitions](https://www.iacr.org/archive/crypto2019/116940405/116940405.pdf).

## Derivability audit

Normal proof runs use `--derivcheck-timeout=0` (derivability checking disabled) and `--quit-on-warning` for the remaining well-formedness checks. Separate derivability runs were inspected. The checker cannot derive witness variables bound by logical verification patterns: AMF signing secrets under `pk`, delegation signing secrets, pairing DH exponents, and hidden credential-proof fields. The ODA `hidx` matches check an invariant shape and only copy the surrounding hash; they never release its preimage. The derived-key reveal pattern similarly copies the complete `kdf(inputs)` term without exposing `inputs`. The enrollment premises used for proof bookkeeping are explained below. These variables remain inside their original opaque terms or are used to check equality. The use is intentional; it is not evidence that the party can compute the witness.

These are manually audited modeling assumptions, not clean automated derivability-check results. Fresh separate audits of the current authentication and ODA sources each reached the 30-second derivability-check limit and returned inconclusive warnings. Pairing reported the intentional delegation-signature/DH-witness patterns; the focused key-derivation comparison passed. These are not clean automated derivability audits of the three protocol models. Each audit log records its exact source hash and command. This is separate from the completed lemma proofs and is not counted as an unresolved protocol claim. See [VALIDATION.json](review/audits/VALIDATION.json) and the audit logs inside [evidence.tar.gz](review/evidence/). Tamarin documents both these diagnostics and intentional pattern matching in its [modeling guidance](https://tamarin-prover.com/manual/master/book/010_modeling-issues.html) and [book, group-element checks](https://tamarin-prover.com/book/downloads/Tamarin%20book-Draft%20v0.9.pdf).

## Scope and reveals

- Participants and sessions are unbounded. Authentication models one CA round per injected state; ODA permits repeated ICV rounds. Linear local states prevent duplicate local processing, but the theories do not implement a global lock or the paper’s tie-break across all exchanges for the same device pair. Finite constraints in ODA's `exists-trace` sanity checks select one honest execution; security lemmas impose no such bounds.
- Authentication and ODA start from an injected, agreed secret pairing state. ODA’s compact CA prefix uses directly enrolled peers and omits identity/token verification and fine timestamps; the full CA theory checks direct and delegated authentication separately. These are conditional component proofs. Proving pairing separately is **not** a composition theorem for provisional caller state, fallback, retries, or complete multi-call state management.
- Enrollment generates whole bundles honestly; arbitrary mixed-component adversarial registration is outside the abstraction. Revealing an enrolled bundle supplies attacker-controlled endpoint secrets. Enrollment tokens and delegation signatures are published deliberately, matching the protocol, which sends `dlgt = (ex_D, ipk_D, sigma_D)` in the clear at pairing. The delegation token itself, which carries the owner's identity, is held by the delegate; the authentication theory releases it only through `Reveal_Dtk` (delegate compromise), and a delegated call records the owner's identity as sent under the call key. This tests pairing when enrollment credentials are already known. Identities are fresh symbolic atoms, so dictionary/candidate testing and observational privacy are not represented.
- Pairing recipient secrecy/agreement target honestly generated, enrolled peer bundles. Attacker-owned or unregistered delegate keys are not secrecy targets. Honest delegation generation chooses enrolled delegates; owner-key compromise allows construction of other signed delegation terms.
- Alice’s pairing record is unconfirmed. The caller-side diagnostic asks whether saving that record implies that Bob previously replied. Tamarin found a counterexample using an adversary-generated token proof and response, without a matching prior Bob response or exposure of either relevant device’s long-term keys. The honest Alice process follows its prescribed steps. This differs from Alice deliberately simulating a transcript with her own secrets: it demonstrates one permitted execution, not deniability by indistinguishability. Alice’s derived-key secrecy remains a separate proved property. Confirmation through CA concerns an honest Alice processing network input; it is not a transferable proof that she could not have simulated a transcript.
- The trusted ES and credential issuer are uncompromised. Enrollment itself is idealized; number assignment, revocation, expiry, timestamps, and the ring-time window are not verified. Multiple bundles may be attested for the same number.
- The single-round authentication theory retains a persistent record allowing its injected input key to be revealed at any time, including after completion. This is a conservative exposure capability for its claims, not a device storage history or a proof of deletion. Pairing has no shared-key reveal.
- `Reveal` releases a whole long-term bundle. `RevealState` releases the shared key independently; it does not reveal temporary DH exponents. In ODA, each local exchange has one linear `CurrentKey` fact. A key update consumes that fact and creates one for the replacement. A reveal is possible only while the corresponding device retains that key. The two reveal rules cover the exhaustive key shapes: an injected fresh pairing key or a KDF output. A flag permits one reveal per local key copy, since repeated revelation gives no additional knowledge; both flag values permit the next update. The peer may still retain its copy while a response is in transit. After both devices delete a key, it cannot be newly revealed, but the attacker permanently remembers any copy already stolen. `RevealId` in authentication separately releases identity data. Credential theft and dishonest credential issuance are outside scope.
- Authentication and agreement lemmas exclude a relevant long-term reveal **anywhere in the trace** and should not be advertised as post-compromise theorems. The key-secrecy lemmas `pair_K_forward_secret_B`, `pair_K_forward_secret_A_genuine`, and ODA's `authenticated_share_origin`, `dh_shared_secret`, and `derived_key_secret` excuse a long-term reveal only **before** the accepted share, DH result, or derived key, so a later reveal does not expose earlier keys. Alice's provisional pairing key has this property only when Bob sent the accepted response; `pair_K_forward_secret_A_expected_falsified` exhibits the fabricated-response exception (a later reveal of Bob's decryption key opens Alice's recorded final message).
- `KU` in secrecy lemmas is Tamarin's internal attacker-knowledge construction event. Excluding it also excludes a network-knowledge `K` event for that term. Helpers use `KU` to constrain derivations; the added identity confidentiality theorem uses the standard `K` target.
- ODA's post-CA state implements the specified lifecycle: ICV accepts only using the state produced by completed CA. This proves ordering for that lifecycle. It does not prove an implementation safe if it accepts ICV using the pre-answer pairing key. Recipient consent is an explicit honest action, never an attacker message.
- Credential attributes `$attr` are public symbolic inputs. `oda2_presentation_secret` checks transport confidentiality of presentation material supplied privately by the assumed credential component, which does not separately publish or disclose it. It does not establish secrecy of public attributes or make an already known payload secret. The current representation still has the structured `pok` term above; it is not a proved generic-payload or UC composition theorem.
- Key-secrecy coverage: pairing proves secrecy of its output. Authentication’s `state_secret` covers its installed starting key, and its key-agreement lemmas compare the two replacement keys. ODA’s `derived_key_secret` additionally proves secrecy of every key produced by its CA prefix and unbounded ICV updates, provided that exact key is never exposed and the relevant long-term keys are not exposed before the derivation. It permits exposure of other shared keys and later long-term-key exposure. `icv_request_authentic`, `icv_display_authentic`, and `icv_key_agreement` add request and presentation authenticity and requester/prover agreement on the replacement key; the last admits exposure of the current shared key. The proof establishes secrecy of the temporary exponents, authentic origin of accepted public shares, and secrecy of the DH result before proving KDF-output secrecy. Knowing the input shared key and transcript alone therefore does not reveal the replacement. These are conditional component results, not a complete composition or a recovery guarantee after theft of temporary DH secrets or long-term authentication keys. The authentication theory also re-verifies the delegation chain at call authentication (`del1_delegation_chain`, with helpers `dlg_key_secret` and `dlg_sig_origin`), and pairing states caller authorization of the accepted key directly (`pair_caller_key_authorized`).
- ODA encrypts both request and presentation under the round’s input key. Its replacement protects subsequent traffic. `presentation_key_origin` connects each presentation’s protecting key to a prior CA or ICV derivation. `oda2_presentation_secret` then proves confidentiality of the privately supplied presentation under the stated exposure and credential-interface conditions. Its formula permits the attacker to remember shared keys stolen during other rounds. Exposure of the exact protecting key is an exception anywhere in the execution, including afterward.
- ODA disclosure control (CA/answer/consent ordering) and transport confidentiality are separate obligations. `oda2_no_harvesting` combines the proved recipient answer rule with the recipient instance of presentation confidentiality. Its proof reuses those results and adds no independent requirement. Absence of an explicit key exposure is not installed as an assumption that the key is underivable; the key-secrecy helpers prove underivability.
- `executable_after_state_exposure` demonstrates a complete credential exchange after its input key is stolen, with long-term keys unexposed. It prevents interpreting the security results as depending on the model stopping after compromise. The presentation in that exposed round is not promised confidentiality; the replacement-key theorem concerns the next key.

## Proof instrumentation and redundant patterns

`DhExp`, `FreshShare`, `AuthShare`, `DhSecret`, and `DerivedKey` record protocol events for the supporting proofs. They neither disclose values nor constrain executions. The additional `Ltk` premises in ODA receive/update rules expose enrollment provenance to the proof search. They are redundant: `Inject_PairState` already requires both enrolled bundles, every subsequent state preserves their number/bundle fields, and `Ltk` facts persist. These premises do not represent access to the peer’s private keys by a device. Similarly, explicit `h(hidx)` index patterns preserve the hash shape established at CA/ICV initiation, and `$attr` preserves the public attribute type already enforced by `Issue_Cred`. These annotations avoid repeatedly reconstructing preceding rounds to rediscover those facts. The key derivations and authenticated message contents are unchanged by these proof aids.

## Interpretation of C-AUTH-4

An identity is shared across a participant’s caller and recipient roles. A participant can send its identity as a caller, and the attacker can learn it after the matching session state is exposed, even if nobody ever answers.

The claims distinguish (1) authorized disclosure in either role, (2) recipient transmission occurring only at answer, and (3) network confidentiality of transmitted identities until the matching state is exposed, except explicit identity compromise or public delegation. The current-protocol report includes an example of caller disclosure under shared-state exposure. Boundary checks appear in the [findings’ supporting checks](MODELING_FINDINGS.md#supporting-verification-checks). No protocol change can make an already disclosed stable identity globally secret again.
